# redis-startup-diag

Диагностика проблемы: веб-сервисы в Kubernetes с go-redis v9 `ClusterClient`
(плюс хуки логов, метрик и трейсов) на старте ловят `i/o timeout` от Redis
Cluster, который живёт на виртуалках. Если перед стартом клиента сделать
«TCP-прогрев» (подключиться к каждой ноде и выполнить AUTH), дальше всё
работает.

Второй похожий случай: при `CLUSTER FAILOVER` слейва в другом ДЦ (всего их
три) на новом мастере тоже посыпались `i/o timeout`, сами не прошли, помог
`rollout restart` приложений. Последующие переключения мастера и слейвов
ошибку не повторили. Разбор — в разделе
[«Таймауты после failover»](#таймауты-после-failover).

Ниже все гипотезы, почему так может быть, как проверить каждую и что делать.
Утилиты в репозитории помогают отличить одну гипотезу от другой.

## Короче

- Сам TCP прогреть нельзя. Ваш прогрев-коннект закрывается и ничего не
  передаёт соединениям go-redis. Значит, он помогает **косвенно**: либо даёт
  время сети или процессу «проснуться», либо убирает залп соединений на старте.
- При `PoolSize = 10000` (это **на каждую ноду**) холодный пул под нагрузкой
  открывает по соединению на каждый одновременный запрос. Локально 3000
  воркеров дали **2397 одновременных dial'ов и 4300 соединений**, а при
  `PoolSize = 50` хватило **151 соединения**, и пропускная способность при этом
  выросла (268k против 167k операций за 4 с). Это главный подозреваемый (H4),
  а H5–H7 описывают, как именно залп ломается об инфраструктуру.
- Первым делом снизить `PoolSize` до 50–200 и прогревать через сам клиент
  (`ForEachShard` + `PING`), а readiness выставлять только после этого.
- Случай с failover укладывается в ту же картину: залп приходит не от старта
  пода, а от того, что все поды одновременно переносят нагрузку на холодную
  ноду. Маленький `PoolSize` с потолком `MaxActiveConns` лечит оба случая.

| `cmd/netprobe` | Без go-redis. С момента старта пода по очереди коннектится к каждой ноде (dns, dial, AUTH+PING) и показывает, когда сеть «ожила». Режим `-burst N` открывает N соединений на ноду одновременно | H1, H2, H3, H5, H6, H7 |

Сборка:

```sh
go build -o bin/ ./cmd/...
# или образ
docker build -t <registry>/redis-startup-diag:latest .
```

Команда `startup` по умолчанию делает только `GET` несуществующих ключей
(`redis-startup-diag:*`), то есть ничего не пишет. Но она создаёт нагрузку и
**много соединений**, поэтому на проде начинайте с `-workers 200`.

## Без exec в поды

`kubectl exec` недоступен, а значит, недоступны и `kubectl cp` (он работает
через exec), и, скорее всего, `kubectl debug`. Поэтому всё здесь устроено так,
чтобы результат приходил через логи, метрики или сетевые ручки.

| Где смотреть | Как запустить | Как получить результат |
|---|---|---|
| Новый под, как у сервиса | `deploy/k8s/job.yaml` | `kubectl logs job/redis-startup-diag` |
| k8s-нода (conntrack, SNAT, SYN) | `deploy/k8s/node-diag-job.yaml` с `nodeName` и `CAPTURE_SECONDS`, запускать **до** роллаута или failover | `kubectl logs job/redis-node-diag` |
| Виртуалки с Redis | `scripts/vm-check.sh` по ssh | stdout |
| Сам сервис, в момент проблемы | `pkg/redisdiag` в коде сервиса | логи сервиса, HTTP или gRPC ручки |
| Всё остальное | метрики | Prometheus/Grafana, запросы ниже |

`node-diag-job.yaml` требует `hostNetwork` и `NET_ADMIN`/`NET_RAW`, то есть
уровня Pod Security `privileged`. Если в ваших неймспейсах это запрещено,
либо попросите платформенную команду запустить его, либо опирайтесь на
метрики node-exporter (ниже).

### Диагностика внутри сервиса: `pkg/redisdiag`

Самый полезный вариант: сервис сам рассказывает, что происходит с его пулами,
ровно в момент проблемы — и при старте, и при failover. Подключение:

```go
rdb := redis.NewClusterClient(opt)
// сразу после создания, ДО первой команды: OnNewNode видит только новые ноды
rdiag := redisdiag.InstrumentCluster(rdb, redisdiag.Options{Logger: slog.Default()})
defer rdiag.Stop()

// HTTP: на внутреннем/админском порту, не на публичном
adminMux.Handle("/debug/redis/", rdiag.Handler())

// gRPC: на внутреннем сервере (модуль github.com/DmitriiTrifonov/redis-startup-diag/grpcdiag)
grpcdiag.Register(adminGRPCServer, rdiag)
```

Что пишется в логи сервиса:
- `redis dial failed` — каждый неудачный dial: адрес, сколько длился, причина
  (`timeout_dial`, `refused`, `no_local_port`, ...), сколько dial'ов было в
  полёте в этот момент;
- `redis slow dial` — dial дольше 200 мс (настраивается `SlowDial`);
- `redis pool stats` раз в 5 с по каждой ноде, где что-то изменилось: сколько
  соединений открыто по требованию, таймауты ожидания пула, всего/idle,
  максимум одновременных dial'ов, ошибки команд по причинам (`timeout_read`,
  `moved`, `loading`, `maxclients`, ...);
- внутренний лог go-redis (перезагрузка топологии, отказы нод).

Ручки:

| HTTP | gRPC (`redisdiag.v1.RedisDiag`) | Что отдаёт |
|---|---|---|
| `GET /debug/redis/` | `Snapshot` | опции клиента (без пароля), GOMAXPROCS, по каждой ноде: соединения, открыто по требованию, таймауты пула, dial'ы всего/в полёте/максимум, латентность последних 1024 dial'ов, ошибки по причинам, последние тексты ошибок |
| `GET /debug/redis/events?last=50` | `Events {"last": 50}` | журнал последних событий с временем: неудачные и медленные dial'ы, создание клиентов нод, всплески пула, внутренний лог go-redis |
| `GET /debug/redis/probe?timeout=2s` | `Probe {"timeout": "2s"}` | по каждой ноде текущей топологии: свежий TCP-dial мимо пула, `PING` через пул и счётчики из `INFO` (`connected_clients`, `rejected_connections`, `sync_full`, `latest_fork_usec`, ...) |

Проба отвечает на главный вопрос «сеть, пул или Redis?»:
- `tcp_dial` медленный или с ошибкой → сеть или backlog на VM (H1, H2, H5, H7);
- `tcp_dial` быстрый, а `pool_ping` медленный или с ошибкой → проблема в
  пуле или в Redis (H4, H5, H9, F2);
- оба быстрые, а сервис ловит таймауты → смотреть хуки и CPU (H9, H10).

Проба открывает одно TCP-соединение на ноду и выполняется одна за раз
(повторный вызов получит 409 / `RESOURCE_EXHAUSTED`).

Как достучаться до ручек без exec:
- через Service или внутренний ingress на админский порт;
- `kubectl port-forward pod/<pod> 8090` — это отдельное право
  (`pods/portforward`), его могут дать, даже если exec запрещён;
- Job внутри кластера, который сам опрашивает ручки и печатает ответ в лог:
  `wget -qO- http://<pod-ip>:8090/debug/redis/probe` или
  `grpcurl -plaintext -import-path /proto -proto redisdiag.proto -d '{}' <pod-ip>:9090 redisdiag.v1.RedisDiag/Probe`.

Попробовать ручки можно на `startup`: `startup -admin-addr :8090 ...`
поднимает их на этом адресе.

`grpcdiag` вынесен в отдельный Go-модуль, чтобы корневой модуль не тянул
gRPC. После клонирования: `cd grpcdiag && go mod tidy`. Интеграционный тест:
`REDIS_ADDRS=127.0.0.1:7000 REDIS_PASSWORD=secret go test ./...`.

Замечание, найденное при тестировании `redisdiag`: команды инициализации
соединения (`HELLO`, `AUTH`, `CLIENT SETINFO`) проходят через хуки нод.
Значит, ваши интерсепторы логов, метрик и трейсов выполняются и на каждом
handshake. При залпе в тысячи соединений это тысячи лишних спанов и записей
в лог именно в момент перегрузки (см. H9). На Redis < 7.2 `CLIENT SETINFO`
ещё и возвращает ошибку, которую go-redis игнорирует, а интерсепторы могут
записать как ошибку команды.

### Метрики вместо exec

Если стоят node-exporter, cAdvisor и redis_exporter (названия метрик зависят
от версий экспортёров):

| Что | PromQL | Гипотеза |
|---|---|---|
| Переполнение accept-очереди на VM с Redis | `rate(node_netstat_TcpExt_ListenOverflows[1m])`, `rate(node_netstat_TcpExt_ListenDrops[1m])` | H5, F1 |
| SYN cookies на VM | `rate(node_netstat_TcpExt_SyncookiesSent[1m])` | H5, F4 |
| Ретрансмиты SYN на k8s-нодах | `rate(node_netstat_TcpExt_TCPSynRetrans[1m])` | H1, H2, H5, H7 |
| Заполненность conntrack на k8s-нодах | `node_nf_conntrack_entries / node_nf_conntrack_entries_limit` | H7 |
| Гонка SNAT и дропы conntrack | `rate(node_nf_conntrack_stat_insert_failed[1m])`, `rate(node_nf_conntrack_stat_drop[1m])` | H7 |
| Троттлинг CPU подов | `rate(container_cpu_cfs_throttled_periods_total[1m]) / rate(container_cpu_cfs_periods_total[1m])` | H10 |
| Соединения и отказы Redis | `redis_connected_clients`, `rate(redis_connections_received_total[1m])`, `rate(redis_rejected_connections_total[1m])` | F1, H6 |
| Fork на Redis | `redis_latest_fork_seconds` (или аналог `latest_fork_usec`) | F4 |

Смотреть их нужно на окне в несколько минут вокруг старта сервиса или
failover. Всплеск `connections_received` на одной ноде одновременно с
`ListenOverflows` на её VM — это прямое подтверждение F1/H4+H5.

## Гипотезы

Для каждой гипотезы указано, объясняет ли она, почему ваш TCP-прогрев помогает.
Если не объясняет, гипотеза менее вероятна.

### H1. Сеть пода не готова в первые секунды

**Суть.** CNI (Calico, Cilium, Antrea и т. п.) настраивает правила и
NetworkPolicy для нового пода асинхронно. Контейнер уже запущен, а первые SYN
наружу ещё дропаются или уходят в никуда. То же бывает, если на виртуалках или
в облачных security groups стоит allowlist по IP подов, который обновляется с
задержкой.

**Почему прогрев помогает.** Прогрев работает как ожидание с ретраями: пока он
идёт, правила успевают примениться.

**Как проверить.**
- `netprobe -duration 15s` первой командой в поде: ошибки только в первые
  секунды, потом ноль, и `first_ok_at` сильно больше нуля.
- Вместо прогрева сделать `sleep 5` перед стартом клиента. Если это тоже лечит,
  дело во времени, а не в коннекте.
- `tcpdump` на ноде: SYN не выходит с ноды или выходит, но ответа нет.

**Что делать.** Ждать сеть в `initContainer` (тот же `netprobe` или цикл
`nc -z`), прогрев с ретраями оставить. В Calico посмотреть настройки
policy-sync, в Cilium — `endpoint-status`.

### H2. Дорогой первый пакет на пути от пода до виртуалки

**Суть.** Первый пакет нового потока на пути pod → нода → шлюз → VM проходит
медленный путь: резолв ARP/neighbor, создание записи conntrack и SNAT на ноде,
установка flow в SDN (OVS/OpenStack, NSX, облачный VPC), stateful firewall или
security group на гипервизоре либо на самой VM.

**Почему прогрев помогает.** Частично: ARP и flow на уровне хост-хост
остаются тёплыми. Но новые соединения с новыми портами всё равно создают новые
записи conntrack и flow, поэтому одна эта гипотеза плохо объясняет, почему
после прогрева всё хорошо.

**Как проверить.** В `netprobe` первая попытка к каждой ноде заметно медленнее
последующих. `tcpdump` на ноде показывает, что SYN ушёл, а SYN-ACK пришёл
поздно.

**Что делать.** Чаще всего достаточно ретраев на старте. Если задержка
стабильно большая, это вопрос к сетевой команде или облаку.

### H3. DNS

**Суть.** Если в `Addrs` или в топологии кластера (`cluster-announce-hostname`)
используются имена, то в k8s при `ndots:5` каждый резолв сначала перебирает
search-домены. На холодном CoreDNS или node-local-dns это медленно. Отдельно
известна проблема с гонкой conntrack для UDP, когда параллельные A- и
AAAA-запросы теряются и резолв занимает ровно 5 с.

**Почему прогрев помогает.** Прогрев греет кэш DNS (node-local-dns, CoreDNS),
и потом клиент резолвит быстро.

**Как проверить.** `netprobe` при именах печатает `dns=...`. В `envreport`
смотреть `resolv.conf`. Таймауты кратны 5 с — признак гонки conntrack.

**Что делать.** Использовать IP или FQDN с точкой на конце, поставить
`ndots: 1–2` в `dnsConfig` пода, включить `single-request-reopen` или
node-local-dns.

### H4. Шквал соединений из-за огромного PoolSize (главный подозреваемый)

**Суть.** `PoolSize` в `ClusterOptions` задаётся **на каждую ноду**. Пул
ленивый: на холодном старте каждый одновременный запрос, не найдя свободного
соединения, открывает новое. Сервис получает трафик, сотни или тысячи горутин
одновременно идут в Redis, и получается сотни или тысячи одновременных TCP
handshake плюс `HELLO`/`AUTH`/`CLIENT SETINFO` на каждую ноду. Дальше залп
ломается об H5, H6 или H7.

Локальный прогон `startup` (3000 воркеров, 3 мастера на одной машине):

| PoolSize | Одновременных dial'ов (макс.) | Соединений | Операций за 4 с |
|---|---|---|---|
| 10000 | 2397 | 4321 | 167k |
| 50 | 149 | 151 | 268k |

Большой пул не ускоряет: одно соединение спокойно держит десятки тысяч
операций в секунду, а тысячи соединений только нагружают Redis и ядро.

Ещё одна деталь go-redis: в пуле есть «предохранитель», который после
`PoolSize` ошибок dial подряд начинает отдавать последнюю ошибку сразу. При
`PoolSize = 10000` он почти никогда не срабатывает, поэтому горутины честно
ждут полные `DialTimeout`/`ReadTimeout`, и приложение выглядит зависшим.

Если `PoolSize` не задан, по умолчанию он считается как `k × GOMAXPROCS`
(в зависимости от версии v9 это 5 или 10 для кластера). На Go до 1.25 без
automaxprocs `GOMAXPROCS` равен числу ядер **ноды**, а не лимиту пода.

**Почему прогрев помогает.** Прогрев занимает время и выполняется
последовательно. Клиент стартует чуть позже, трафик и инициализация
приложения размазываются, а топология кластера уже загружена. Залп всё ещё
есть, но он мельче или приходит в момент, когда Redis и сеть уже не заняты
другим.

**Как проверить.**
- `startup -pool-size 10000 -workers <ваш RPS × латентность>`: смотреть
  `max_inflight_dials` и строку `dials`.
- То же с `-pool-size 100`, с `-ramp 5s` и с `-warmup ping`. Если ошибки
  пропадают — это H4.
- В метриках сервиса посмотреть `PoolStats().TotalConns` и `Timeouts` в первые
  секунды после старта.

**Что делать.**
- `PoolSize: 50–200` на ноду. Если пул реально исчерпывается, это будет видно
  по `PoolStats().Timeouts`, и тогда поднять.
- `MinIdleConns` маленький (0–10): он открывает соединения залпом сразу.
- `MaxActiveConns` как жёсткий потолок.
- В новых версиях v9 у `Options` есть `MaxConcurrentDials` и `DialerRetries`.
  Проверьте версию в своём `go.mod` и наличие этих полей в `ClusterOptions`.
- Прогрев через клиент и readiness после него (см. H12).

### H5. Redis на виртуалке не успевает принимать соединения

**Суть.** Redis принимает соединения в одном потоке. На каждое новое соединение
нужно `accept`, а затем выполнить `HELLO`, `AUTH`, `CLIENT SETINFO` (×2) в том
же event loop, где идут обычные команды. Тысячи одновременных handshake
занимают его, ответы опаздывают, и клиент получает `i/o timeout` на чтение.

Есть и сетевая часть. Очередь accept ограничена `tcp-backlog` (по умолчанию
511), но фактически это минимум из `tcp-backlog` и `net.core.somaxconn` на VM.
Когда очередь полна, при `tcp_abort_on_overflow = 0` Linux **молча
выбрасывает финальный ACK**. Клиент считает, что соединение установлено,
отправляет `AUTH` и ждёт ответа, а сервер про соединение ещё не знает. В
результате вы видите **i/o timeout на чтение, а не на dial** — ровно ваш
симптом.

**Почему прогрев помогает.** Если залп мельче или приходит позже, очередь не
переполняется.

**Как проверить.**
- `vm-check.sh` до и после раскатки: растут `TcpExtListenOverflows` и
  `ListenDrops`, `ss -lnt` показывает Recv-Q около Send-Q.
- `netprobe -duration 0 -burst 500`: латентность dial ступеньками около 1 с и
  3 с (ретрансмит SYN), или `cmd_timeout_read` при быстром dial.
- `startup`: `dials_ok` заметно больше `conn_init_ok`.
- `INFO stats`: всплеск `total_connections_received` на старте.

**Что делать.** В первую очередь уменьшить залп (H4). Дополнительно поднять
`net.core.somaxconn` и `tcp_max_syn_backlog` на VM, `tcp-backlog` в Redis (до
4096 и т. п.) и включить `io-threads`, если версия Redis 6+ и CPU позволяет.

### H6. Лимиты соединений на стороне Redis

**Суть.** `maxclients` по умолчанию 10000 на инстанс, а Redis на старте сам
уменьшает его под `ulimit -n` процесса. При `PoolSize = 10000` даже один
под может упереться в лимит, а несколько подов (и несколько сервисов на один
кластер) упрутся точно. Ответ будет `ERR max number of clients reached`, но
в логах с хуками это может выглядеть как обрыв или таймаут, если ошибка
пришла посреди handshake.

**Почему прогрев помогает.** Слабо, только через уменьшение залпа. Если причина
в этом, ошибки будут и после старта при росте нагрузки.

**Как проверить.** `envreport -pool-size ... -nodes ... -pods ... -maxclients ...`
для расчёта; на VM `INFO clients` (`connected_clients`, `maxclients`),
`INFO stats` (`rejected_connections`), лимит fd процесса в `vm-check.sh`.
В `startup` и `netprobe -burst` корзина `maxclients`.

**Что делать.** Уменьшить `PoolSize` (H4). Поднять `LimitNOFILE` в systemd-юните
Redis и `maxclients`, если соединений действительно нужно много.

### H7. Ресурсы ядра на пути: conntrack, SNAT, эфемерные порты

**Суть.** Трафик из пода на VM вне кластера обычно проходит через SNAT
(masquerade) на ноде, и каждое соединение — запись в conntrack.
- `nf_conntrack_max` на ноде переполняется: в `dmesg` будет
  `nf_conntrack: table full, dropping packet`, а новые SYN молча
  дропаются.
- Известная гонка при SNAT: два соединения одновременно получают один и тот же
  порт, второе дропается (`insert_failed` в `conntrack -S`), клиент ждёт
  ретрансмита SYN 1 с и 3 с.
- Эфемерные порты: под с 10k соединениями на одну ноду и быстрым
  пересозданием соединений упирается в `ip_local_port_range` и `TIME_WAIT`.

**Почему прогрев помогает.** Слабо, только через уменьшение залпа.

**Как проверить.** `node-check.sh`: `count`/`max`, `insert_failed`, `drop`,
`TcpExtTCPSynRetrans`. В `netprobe -burst` корзины `dial_timeout_dial` и
`dial_no_local_port`. В tcpdump один и тот же SYN повторяется через 1 с и 3 с.

**Что делать.** Уменьшить залп (H4). Поднять `nf_conntrack_max` на нодах,
использовать `--random-fully` для masquerade (в современных kube-proxy и CNI
обычно уже включено), расширить `ip_local_port_range`.

### H8. Особенности go-redis ClusterClient на старте

**Суть.**
- Топология (`CLUSTER SLOTS`) загружается лениво при первой команде. Пока она
  не загружена, все горутины ждут. Если первая загрузка упала по таймауту, все
  ждавшие получат ошибку.
- Ноды, адреса которых пришли из `CLUSTER SLOTS` (`cluster-announce-ip`), могут
  отличаться от seed-адресов в `Addrs`. Ваш TCP-прогрев идёт только на seed'ы.
- После ошибок нода помечается как failing и какое-то время избегается, что
  портит маршрутизацию и даёт лишние `MOVED`/повторы.
- В свежих v9 у `ClusterOptions` по умолчанию `MaxRetries = -1`: ретраев нет,
  кластерный клиент повторяет только при редиректах. Один таймаут сразу
  становится ошибкой для приложения.

**Почему прогрев помогает.** Если прогрев делается через клиент (как
`-warmup ping`), он загружает топологию заранее. Ваш TCP-прогрев этого не
делает, так что это объясняет лишь часть.

**Как проверить.** Внутренний лог go-redis в `startup` (`-internal-log`,
включён по умолчанию) показывает ошибки загрузки состояния кластера и
переключения нод с таймстемпами. Сравнить `-warmup tcp` и `-warmup ping`.

**Что делать.** Прогрев через `ForEachShard` + `PING` с ретраями и backoff.
Явно задать `MaxRetries: 2–3` и `MinRetryBackoff`/`MaxRetryBackoff`, если
повторы для ваших команд безопасны.

### H9. Хуки логов, метрик и трейсов

**Суть.** Хуки выполняются синхронно в пути каждой команды, а трейсинг и
метрики через `OnNewNode` — ещё и на каждом соединении. Если на старте:
- OTel использует `SimpleSpanProcessor` (синхронный экспорт), а коллектор
  ещё недоступен или медленный;
- логгер пишет каждую команду синхронно в stdout/файл, а stdout в контейнере
  медленный;
- регистрация метрик на новую ноду берёт глобальную блокировку;

то время внутри хука съедает бюджет `ReadTimeout`/контекста, и команды падают
по таймауту, хотя Redis ответил вовремя.

**Почему прогрев помогает.** Пока идёт прогрев, экспортёры трейсов и метрик
успевают подключиться к коллектору.

**Как проверить.** В сервисе временно отключить хуки и раскатить. В `startup`
можно сымитировать тяжёлый хук: `-hook-delay 50ms`. Убедиться, что для трейсов
используется `BatchSpanProcessor`.

**Что делать.** Асинхронные экспортёры, логирование команд только при ошибке
или с семплированием.

### H10. Троттлинг CPU пода на старте

**Суть.** На старте приложение делает много работы: инициализация, прогрев
кэшей, тысячи горутин, возможно TLS. При CPU-лимите пода CFS-квота
заканчивается за доли периода, и процесс «замораживается» до следующего. Read
deadline у сокета истекает, пока горутина даже не была запланирована, хотя
ответ Redis уже лежит в буфере. Отсюда `i/o timeout` при здоровой сети и
здоровом Redis.

**Почему прогрев помогает.** Прогрев сдвигает нагрузку на Redis на момент,
когда основной CPU-пик инициализации уже прошёл.

**Как проверить.** Метрика `container_cpu_cfs_throttled_periods_total` и
`..._seconds_total` пода в первые секунды. В `envreport` — `cpu.max`.
Временно убрать CPU-лимит или поднять его вдвое и посмотреть, уйдут ли ошибки.

**Что делать.** Убрать или поднять CPU-лимит (оставить requests), выставить
`GOMAXPROCS` под лимит (Go 1.25+ делает это сам, иначе `automaxprocs`), не
выпускать трафик до окончания инициализации (H12).

### H11. TLS (если включён)

**Суть.** TLS-handshake на каждое из тысяч новых соединений — это заметный
CPU и на поде (H10), и на Redis (H5, в Redis TLS тоже в основном потоке, если
не включены `io-threads`).

**Как проверить.** Есть ли `TLSConfig` в опциях. Сравнить `netprobe -tls` в
обычном и `-burst` режиме.

**Что делать.** То же, что в H4: меньше соединений.

### H12. Трафик приходит раньше, чем клиент готов

**Суть.** Readiness-проба не проверяет Redis, и k8s отправляет в под трафик
сразу после старта. Вся нагрузка попадает на холодный пул и незагруженную
топологию — это и запускает залп из H4.

**Почему прогрев помогает.** Прогрев задерживает старт HTTP-сервера, то есть
работает как неявный readiness gate.

**Что делать.**

```go
// при старте, до того как readiness станет OK
ctx, cancel := context.WithTimeout(context.Background(), 30*time.Second)
defer cancel()
backoff := 100 * time.Millisecond
for {
	err := rdb.ForEachShard(ctx, func(ctx context.Context, c *redis.Client) error {
		return c.Ping(ctx).Err()
	})
	if err == nil {
		break
	}
	if ctx.Err() != nil {
		log.Fatalf("redis not ready: %v", err)
	}
	time.Sleep(backoff)
	backoff = min(backoff*2, 2*time.Second)
}
// теперь можно выставлять ready
```

Плюс `startupProbe`/`readinessProbe` на эндпоинт, который отвечает OK только
после этого.

## Таймауты после failover

### Что было

- Три ДЦ. Слейв в одном ДЦ сделали мастером через `CLUSTER FAILOVER`
  (переключение запускали со стороны другого ДЦ).
- На новом мастере сразу пошли `i/o timeout`, и **сами не прошли**.
- Помог `kubectl rollout restart` приложений.
- Потом мастер и слейвы переключали по-всякому, ошибка **не повторилась**.

Это важная улика. Старт пода тут ни при чём, значит H1 (сеть пода не готова)
и H10 (троттлинг на старте) как единственные причины отпадают. Зато сценарий
ложится на H4 + H5: залп соединений на холодную ноду.

### F1. Залп соединений на новый мастер (главная версия)

**Суть.** Пока нода была слейвом, клиенты к ней почти не ходили: без
`ReadOnly`/`RouteByLatency` все команды идут на мастера, и пула к слейву
фактически нет. После failover все поды одновременно получают `MOVED`,
перезагружают топологию и переносят всю нагрузку этих слотов на новую ноду.
Холодный пул с `PoolSize = 10000` открывает соединение на каждый
одновременный запрос. Получаются тысячи SYN и `HELLO`/`AUTH` от **всех подов
сразу** на одну VM.

Дальше то же, что в H5: переполняется accept-очередь, Linux молча
выбрасывает финальный ACK, клиент считает соединение установленным,
отправляет `AUTH` и получает таймаут на чтении. Плюс однопоточный event loop
Redis занят тысячами handshake. Если по пути есть SNAT или межцодовый
firewall, добавляется H7.

Локальная проверка (`startup` с 2000 воркеров и `failover-test.sh` на одной
машине): за первую секунду после `CLUSTER FAILOVER` один процесс открыл к
новому мастеру **1425 соединений**, и 20 из них установились за **~1,1 с** —
это ретрансмит SYN, то есть очередь не справилась даже на loopback. С десятком
подов, межцодовым RTT и `PoolSize = 10000` залп будет в разы больше.

От старта пода failover отличается тем, что при роллауте поды стартуют по
очереди (`maxSurge`/`maxUnavailable`), а failover бьёт по всем подам
одновременно. Поэтому он хуже.

### F2. Почему не прошло само: метастабильное состояние

Перегрузка поддерживает сама себя:

1. Команда упала по таймауту, go-redis закрывает «плохое» соединение.
2. Следующая команда не находит свободного соединения и открывает новое.
3. Новые handshake снова перегружают ноду, снова таймауты.

Нагрузку держат уже не пользователи, а сами переподключения. Даже когда
исходный всплеск закончился, система не возвращается в нормальное состояние.
Этому помогают отсутствие ретраев с backoff на уровне приложения,
`MaxRetries = -1` по умолчанию у кластерного клиента в свежих v9 и то, что при
`PoolSize = 10000` предохранитель пула (H4) почти никогда не срабатывает.

**Почему помог `rollout restart`.** Поды перезапускаются по очереди. Старые
поды с «больными» пулами уходят, новые приходят по одному, нагрузка на ноду
растёт постепенно, и петля рвётся.

### F3. Почему потом не повторялось: тёплые пулы

После того как нода снова становится слейвом, её node-клиент в go-redis
**не удаляется**: нода остаётся в топологии, а пул к ней остаётся с
соединениями. Устаревшими они считаются только через `ConnMaxIdleTime`
(по умолчанию 30 минут; проверяется при взятии соединения из пула).
Если в Redis `timeout` не 0, сервер закроет их раньше.

Значит, если в экспериментах мастер крутили туда-обратно в пределах
получаса, пулы к обеим нодам были тёплыми, и залпа не было. Вчерашний
сценарий — **холодный слейв, к которому давно никто не ходил, впервые
становится мастером** — скорее всего, не повторяли.

### F4. Другие версии, которые стоит исключить

**Fork на новом мастере.** После промоута старый мастер стал репликой нового.
Если partial resync не удался (мал `repl-backlog-size`, сменился replication
ID, промежуточные переключения), новый мастер делает full sync: fork + RDB +
передача по сети. На VM с большим датасетом fork может морозить Redis на
сотни миллисекунд или секунды, особенно с Transparent Huge Pages. Это даёт
первичный всплеск таймаутов, а F2 превращает его в затяжной.

Проверить:
- лог Redis на новом мастере и на старом: `Full resync requested`,
  `Starting BGSAVE`, `Background saving started`, `Partial resynchronization
  not accepted`;
- `INFO stats`: `latest_fork_usec`, `sync_full`, `sync_partial_ok`,
  `sync_partial_err`;
- `cat /sys/kernel/mm/transparent_hugepage/enabled` на VM (должно быть
  `never` или `madvise`).

**Межцодовый firewall или DDoS-защита.** Тысячи новых соединений разом к
одному IP:port из подсетей k8s могут попасть под лимит новых сессий в секунду,
SYN-flood защиту или лимит на число сессий с одного источника. После SNAT все
поды ноды выглядят как один IP, поэтому лимиты «на источник» срабатывают
быстрее. Это вопрос к сетевой команде: были ли срабатывания в момент
failover.

**SYN cookies на VM.** При переполнении SYN-очереди ядро включает SYN cookies
(`TcpExtSyncookiesSent`). Соединения устанавливаются, но без части опций TCP
(window scaling на старых ядрах), и межцодовый трафик с большим RTT может
резко замедлиться.

**MTU между ДЦ.** Если между ДЦ туннель (VXLAN, IPsec, GRE), а ICMP
`frag-needed` где-то режется, маленькие пакеты (SYN, `AUTH`, `PING`) проходят,
а большие ответы теряются, и это read timeout. Но тогда проблема держалась бы,
пока мастер в том ДЦ, и не лечилась бы рестартом. Важно уточнить, переезжал
ли мастер в **тот же** ДЦ в повторных экспериментах. Проверка из пода:
`ping -M do -s 1472 <ip>` (и меньше, пока не пройдёт) или `tracepath <ip>`.

**Рост RTT.** Если новый мастер в другом ДЦ, чем большинство подов, каждая
команда стала медленнее на RTT между ДЦ. При той же нагрузке нужно больше
одновременных соединений (закон Литтла), что усиливает F1. Рестарт этого не
меняет, поэтому сам по себе RTT не объясняет случай, но может быть
усилителем.

### Что посмотреть за вчера

| Где | Что | Какая версия |
|---|---|---|
| Новый мастер, метрики Redis | `connected_clients`, `total_connections_received` в момент failover | F1 |
| Новый мастер, ядро | `nstat TcpExtListenOverflows TcpExtListenDrops TcpExtSyncookiesSent` (счётчики накопительные, сравнить с сегодняшними) | F1, F4 |
| Лог Redis на обоих | full resync, fork, BGSAVE | F4 |
| `INFO stats` | `latest_fork_usec`, `sync_full`, `rejected_connections` | F4, H6 |
| Метрики сервиса | соединения в пуле и частота dial'ов к новой ноде, ошибки по типам (dial или read timeout) | F1, F2 |
| Сеть | срабатывания firewall / DDoS-защиты между ДЦ | F4 |
| Эксперименты | в какой ДЦ уходил мастер при повторах и сколько времени проходило между переключениями | F3, F4 |

### Как воспроизвести

Нужен холодный слейв, к которому пулы приложений давно не ходили.

1. Не переключать мастера минимум 30–40 минут (больше, чем `ConnMaxIdleTime`
   по умолчанию, или больше вашего значения).
2. Запустить нагрузку из пода в кластере и оставить работать:
   `startup -pool-size 10000 -workers 1000 -duration 600s -warmup ping`
   (или сам сервис на стейдже).
3. На целевой VM: `scripts/vm-check.sh <port>` до переключения.
4. Сделать failover скриптом `scripts/failover-test.sh`: он снимает
   состояние до и после и сам выполняет `CLUSTER FAILOVER` на выбранном
   слейве.
5. В выводе `startup` смотреть на всплеск `started`/`infl` в колонке dials и
   на корзины ошибок. После — `vm-check.sh` ещё раз и сравнить счётчики.
6. Повторить с `-pool-size 100 -max-active 200`. Если всплеск и таймауты
   пропали — это F1.

### Что делать

- `PoolSize` 50–200 и `MaxActiveConns` как жёсткий потолок на ноду. Это
  ограничивает залп на новую ноду при любом failover.
- `MinIdleConns: 0` или маленький. Иначе после смены топологии клиент сам
  откроет все idle-соединения разом.
- `MaxRetries: 2–3` с `MinRetryBackoff`/`MaxRetryBackoff` (если команды
  идемпотентны), а на уровне приложения не ретраить без backoff.
- На VM: `net.core.somaxconn` и `tcp-backlog` 4096+, THP в `never`,
  `repl-backlog-size` с запасом, чтобы после переключения работал partial
  resync.
- В плане переключений: перед failover можно заранее прогреть пулы к целевому
  слейву (например, временно включить `ReadOnly` чтение со слейвов для части
  трафика) или переключать в часы низкой нагрузки.

| Таймауты на новом мастере после failover, проходят только после рестарта | F1 + F2 |
| После failover в логе Redis full resync / fork, большой `latest_fork_usec` | F4 (fork) |
| Таймауты держатся, пока мастер в определённом ДЦ, рестарт не помогает | F4 (MTU, firewall) |

## План прогона

Всё без exec: результаты приходят через `kubectl logs`, логи сервиса, метрики
и ssh на виртуалки.

1. Встроить `pkg/redisdiag` в сервис (логи плюс HTTP или gRPC ручки на
   админском порту) и раскатить. Это само по себе даст картину при следующем
   старте или failover.
2. На каждой VM снять `scripts/vm-check.sh` до эксперимента.
3. Создать ConfigMap со скриптами и запустить `deploy/k8s/node-diag-job.yaml`
   на ноде, где живут поды сервиса, с `CAPTURE_SECONDS=600`.
4. Пока идёт захват: запустить `deploy/k8s/job.yaml` (тот же неймспейс,
   лейблы и ресурсы, что у сервиса) или сделать `rollout restart` сервиса.
   Job выполнит `envreport`, `netprobe`, `netprobe -burst` и `startup` на
   холодном поде.
5. Сразу после — `vm-check.sh` на VM ещё раз. Сравнить счётчики, прочитать
   логи обоих Job'ов и `GET /debug/redis/events` у сервиса.
6. Повторить `startup` с `-pool-size 100`, с `-ramp 5s`, с `-warmup ping`.
   Сравнить.
7. Для failover — сценарий из раздела «Как воспроизвести» выше, с тем же
   node-diag Job'ом и ручкой `/debug/redis/probe` у сервиса до и после.
8. В самом сервисе: `PoolSize: 100`, `MaxActiveConns`, прогрев через клиент,
   readiness после прогрева. Раскатить и посмотреть.

## Локально

```sh
./scripts/local-cluster.sh up                       # нормальный кластер
TCP_BACKLOG=64 MAXCLIENTS=1500 ./scripts/local-cluster.sh up   # «слабый» кластер
export REDIS_ADDRS=127.0.0.1:7000,127.0.0.1:7001,127.0.0.1:7002 REDIS_PASSWORD=secret
go run ./cmd/netprobe -duration 2s -burst 500
go run ./cmd/startup -workers 3000 -duration 10s
go run ./cmd/startup -workers 3000 -duration 10s -pool-size 100
./scripts/local-cluster.sh down
```

Локальный кластер на loopback не воспроизводит H1–H3 и H7: там нет CNI, SNAT
и сети между машинами.
